Questions

The ones that actually come up

Answered from the source, the per-crate READMEs, and captured runs.

Where does the data live?

SurrealDB 2 embedded with the SurrealKV engine, at ~/.ctx/doob/db/ — a directory, not a file. Namespace and database are both doob. Override the location with the global --db flag.

The root README says ~/.claude/data/doob.db. That is wrong.

I edited the status in HANDOFF.yaml and it reverted. Why?

Because the database wins on conflict. That rule is one line in the sync implementation — // doob wins on status conflict — and if the stored status differs from the file, the stored value is written back into the YAML.

So run doob handoff update-status <id> <status> first, then edit the file for anything else. Sync also rewrites the whole document, so keep anything you add in a shape it round-trips.

Which status values apply where?

Two vocabularies, and they are not interchangeable.

Applies toValues
Todos, in the database and the CLIpending · in_progress · completed · cancelled
Handoff items, in the YAML and the TUIopen · done · parked · blocked

A third TodoStatus exists in doob-sync with two variants that serialise as "Pending" and "InProgress". It is part of the provider framework and is not reachable from the CLI.

Is the SQLite backend safe to use?

Not for doob todo add, and the crate README says so. The adapter reads tuple fields as (content, uuid, …) while the command layer passes (uuid, content, …), so content lands in the uuid column.

Archive persistence, raw query execution, and the raw HANDOFF sync operations are also unimplemented, and the command layer falls back to the todo repository as a placeholder for archive. SurrealDB is the supported backend; SQLite is opt-in and partial.

If you must use it, build with --no-default-features --features sqlite, and follow the adapter's current field order rather than the command layer's.

Why is the query code full of string interpolation?

Because parameterised queries silently do nothing in SurrealDB 2.x — tracked upstream as issue 6271. doob-core therefore enforces strict allowlists in a query guard before any user-supplied value reaches a query string. That is a safety control compensating for an upstream bug, not a preference.

The caveat: several todo and archive paths still use .bind(...), so they remain exposed to the bug. The adapter README flags this and asks for real SurrealKV verification rather than compile-only confidence on any change to those paths.

How do I read this for a script?

Put the global flag first: doob --json todo list, not doob todo list --json. Every read path supports it.

Branch on the exit code rather than parsing text. It is a real enum: 0 success, 1 not found, 2 invalid input, 3 database, 4 context, 5 io, 6 parse.

Expect the id to be a nested object, not a string — {"tb": "todo", "id": {"String": "..."}}. The root README shows a flat "todo:abc123", which is not what the binary prints.

Does doob schema give me the full command surface?

No. It emits 15 commands; the real CLI has 29. Absent from the manifest: kan, watch, tui, todo update, todo gh-sync, handoff add-extra, handoff update-status, archive run, and schema itself. Several positional arguments are described as flags.

It is the only place the version is discoverable, since there is no --version flag. Treat it as provisional and read the crate's CLI source for the real surface.

Is there a Linear or Jira integration?

No. doob-sync defines the provider-neutral traits and a SyncService, and doob-sync's README is explicit: the framework is not wired to any doob CLI command, and there are no active GitHub, Linear, Jira, or bidirectional providers.

GitHub support does exist — in doob-gh, which is a separate implementation that does not implement those traits. It shells out to the gh CLI and is push-only: it never reads issue state back, and never updates an existing issue's title or body.

What does removing a todo do to its GitHub issue?

It adds a tombstone comment and leaves the issue open. The comment reads "This todo was removed from doob without being completed."

Completing a todo closes the issue instead. Both behaviours are configurable and both default to true. There is no undo for a remove, which is why this workspace runs a database backup before one.

Does the dashboard depend on doob?

No. doobdash is a binary-only crate with a dependency on nothing in the workspace. It reads the YAML directly and shells out to the installed doob for its two mutations: doob handoff update-status ID STATUS and doob handoff add-extra ID --type note --note TEXT.

Both call sites discard the result, so a failed mutation is not surfaced in the TUI. The DB tab is also unreliable: it queries a namespace and field names the primary adapter does not use.

How do I install it?

From the crate, not the workspace root:

cargo install --path crates/doob
cargo install --path crates/doobdash

For the SQLite build, add --no-default-features --features sqlite. The release is by default; a --release flag is rejected.

It is not on crates.io, and the repository has no GitHub releases, so there is nothing to brew install or download. A single v0.1.0 tag exists from February 2026.

Which document should I trust?

The per-crate READMEs and CLAUDE.md. The root README.md has drifted on the install command, the database path, the JSON id shape, and an entire sync surface that does not exist. docs/sync/ documents commands that were never built.

The per-crate READMEs are the strongest thing in the repository: each opens with a Status section that names its own limitations, including the SQLite safety warning.
