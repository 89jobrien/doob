Four SurrealDB 2.x behaviours the code works around

These are documented in the agent guide, the crate README, and the comments in the adapter, which is unusual for a list this specific — and worth reading before changing any query.

  1. Parameterized queries silently no-op

    Tracked upstream as issue 6271. Values are interpolated into raw SQL instead, which is why doob-core carries a query guard enforcing strict allowlists before anything user-supplied reaches a query string.

  2. Datetimes must be injected as literals

    ISO strings are rejected inside CONTENT; they have to be written as d"2026-01-01T00:00:00Z".

  3. UPDATE ... MERGE ... WHERE returns no rows even on success

    Select first to check existence rather than trusting the update's return.

  4. .take::<Vec<Value>>(0) fails on rows containing Thing

    Use serde_json::Value, or ignore the result.

The adapter's own README adds a caveat: several todo and archive paths still use .bind(...), so changes there need a real SurrealKV run to verify rather than a compile-only check. The four workarounds above and this caveat coexist in the current code.

Feature selection

The doob crate declares default = ["surrealdb"], plus optional sqlite and surrealdb features. When both are enabled the binary selects SQLite: the sqlite cfg block is checked first.

GitHub sync

doob-gh has no HTTP client. It shells out to the authenticated gh binary and never reads GITHUB_TOKEN itself, so authentication is entirely gh's problem.

What each action does
ActionEffect
addgh issue create
completegh issue close
removeAdds a tombstone comment. The issue stays open, marked "This todo was removed from doob without being completed."

Both close_on_complete and tombstone_on_remove default to true. Config lives at ~/.config/doob/gh-sync.toml, with sync state at gh-sync-state.json mapping todo UUID to repository and issue number.

Synchronization is push-only. It does not read issue state back into doob, and it does not update existing issue titles or bodies. Also worth knowing: doob-gh is a separate implementation that does not implement the provider traits in doob-sync — it has zero references to that crate.

Query safety

Because parameterized queries silently do-op, doob-core enforces allowlists before any user value reaches a query string. That is a security control, not a style preference: the crate's own comment frames it as the consequence of the upstream bug rather than a preference for string building.
