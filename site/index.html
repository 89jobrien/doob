What it is for

The database is the source of truth. The YAML is a view of it.

A handoff file lives in the repository so a person can read it without running anything. Sync pulls it into the database, mints a UUID for anything new, writes that UUID back into the file, and merges extra entries in both directions.

On conflict, the database wins

The rule is one line of the sync implementation, and it is the thing to know before editing a handoff file by hand:

// doob wins on status conflict

If the stored status differs from the file, the stored value is written back into the YAML. So call doob handoff update-status before editing status by hand, or the edit is reverted.

The project name comes from the directory

Sync derives the project from the immediate parent folder of the handoff file, not from a project: field in the document. Moving a file moves the records with it.

A handoff item's priority is a label — P0, P1, P2 — not a number, unlike a todo's numeric priority.

The board

Work sits in lanes, and the lanes are the TUI's

The dashboard maps handoff status to three columns. The mapping is source-defined, not a design guess: Active takes open, blocked, and in-progress; Waiting takes parked and waiting; Done takes done.

Two vocabularies

Todos and handoff items do not share a status enum

This trips people up, and the crate README says so explicitly. A todo has four statuses; a handoff item has four different ones.

Todo

Stored in the database

pending · in_progress · completed · cancelled

Defaults in the schema are 'pending' and priority 0. pending is the value the CLI prints and the filter accepts.

Handoff

Stored in the YAML and shown by the TUI

open · done · parked · blocked

Quoted from the dashboard's own README: These are HANDOFF statuses, not the pending/in_progress values used by the todo database.

There is a third TodoStatus in doob-sync with only two variants, and it serializes as "Pending" and "InProgress" in Rust variant casing rather than the snake case the rest of the workspace uses. It is part of the provider framework, which is not reachable from the CLI.

For agents

Built to be called, not read

Shipped

JSON on every read path

--json is a global flag, so doob --json todo list works. The agent guide is explicit that JSON output is a compatibility surface: its shape is a promise.

Shipped

Typed exit codes

Zero success, 1 not found, 2 invalid input, 3 database, 4 context, 5 io, 6 parse. A real enum, classified from the rendered error, so a script can branch without parsing text.

Partial

doob schema

It emits a machine-readable manifest of 15 commands. The real CLI has 29, and the manifest describes several positional arguments as flags. Treat it as provisional.

The dashboard

doobdash reads the file and shells out to change it

A standalone Ratatui binary with five tabs: Items (a three-column kanban), Log, Stats, Help, and an experimental DB view. It does not depend on any doob crate. It reads the YAML directly and shells out to the installed doob for the two mutations it supports.

Its own README is candid about the seams: status and note actions shell out, and failures are discarded by the event handlers rather than shown in the TUI — both call sites discard the result. The DB tab is implemented against a namespace and field mapping that do not match the primary adapter, so it may show no rows.
