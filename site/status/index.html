The SQLite backend, specifically

It is the one place where a partial implementation is more dangerous than no implementation, so it gets its own section.

The tuple-order bug

TodoRepositoryImpl::create_todos reads tuple fields as (content, uuid, …). The command layer and the SurrealDB adapter both pass (uuid, content, …). Until that is reconciled, the SQLite-backed doob todo add path writes content into the uuid column. The crate's own README calls it unsafe for real data.

What is missing

Archive persistence, raw query execution, and the raw HANDOFF sync operations are all unimplemented. The command layer falls back to the todo repository as a placeholder for archive, and says so in a comment.

What is missing in CI

CI runs the default feature set. A SQLite-specific job would be the thing that catches the tuple-order regression, and there isn't one.

Known defects worth knowing

  • Dashboard mutations fail silently. Both subprocess call sites discard the result, so a failed status change produces no error in the TUI.
  • search --type accepts anything. Only todo and note are meaningful; any other value silently behaves as all.
  • Schema is incomplete. The manifest lists 15 commands against 29 real ones. kan, watch, tui, todo update, todo gh-sync, handoff add-extra, handoff update-status, archive run, and schema itself are all absent, and several positional arguments are described as flags.
  • The adapter still uses .bind. Several todo and archive paths do, which means they are exposed to the parameterised-query bug the rest of the code works around. The adapter README flags this explicitly.
  • The repository ships one licence file. All eight manifests declare MIT OR Apache-2.0; only the MIT text is present.

Documentation that contradicts the code

Root README.md cargo install --path . cannot work — the root is a virtual manifest. The database path is given as ~/.claude/data/doob.db; it is ~/.ctx/doob/db/. The JSON example shows a flat "todo:abc123" id where the real output nests a Thing. It lists four planned sync adapters and a sync command that do not exist.

AGENTS.md and CLAUDE.md Both claim ci.sh runs cargo deny check. It runs cargo audit; cargo deny is in the GitHub workflow only. Both also claim there is no justfile, and a tracked Justfile exists.

The per-crate READMEs and CLAUDE.md are the accurate sources. Read those instead of the root README.
